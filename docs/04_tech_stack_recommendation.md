# 考公平台技术栈评估与选型建议

基于项目的三大核心诉求：“多平台兼容（微信小程序+网页端）”、“多模态数据处理（图文混合解析）”以及“长远的高并发及大模型集成”，我为你提供以下最贴合业务现状的技术架构建议：

## 1. 前端框架选型 (Frontend)
- **已确认方案：Taro (React/Vue)**
- **核心理由**：完美契合你的跨端需求，能够直接编译为微信小程序，也能生成网页端，极大节约多端维护成本。

## 2. 核心数据库选型 (Database)
- **已确认方案：PostgreSQL**
- **核心理由**：对于包含多样化选项和复杂题干（非结构化数据）的考公题目，Postgres 的 JSONB 字段提供了极大的灵活性，且支持优秀的事务与检索性能。

## 3. 文件与多媒体存储 (Storage) - 【自建服务器探讨】
既然你已经拥有不限流量的独立服务器，出于节约成本和避免网络延迟的考虑不愿使用第三方云 OSS，这是非常合理的决策。针对单机/集群自建存储，业界有以下三种方案的对比：

### 方案 A：直接存放在本地文件系统 (Local FS + Nginx)
将图片存放在 Linux 的某个目录下（如 `/var/www/uploads`），由 Nginx 直接提供静态资源下载服务。
- **性能开销**：**极低**。Nginx 处理静态文件的性能无可匹敌，通过系统的 `sendfile` 零拷贝机制，几乎不占用 CPU，性能瓶颈仅在于服务器的带宽和硬盘 I/O。
- **备份机制**：基于文件系统的常规备份。可以通过写个脚本每天用 `rsync` 增量同步到另一台机器，或者打包成 `tar.gz`。
- **优点**：极其简单粗暴，无需额外学习，开箱即用。
- **缺点**：扩展性极差。如果后期用户暴增，你需要增加一台服务器做负载均衡时，两台服务器之间的文件同步（如 `NFS` / `Unison`）会非常痛苦；且缺乏现代化的图片处理能力（如动态加水印、动态缩放）。

### 方案 B：使用数据库存储 (MongoDB GridFS 或 Postgres BYTEA)
将图片转化为二进制流直接存入数据库中。
- **性能开销**：**极高（性能灾难）**。每次拉取一张图片，都需要建立数据库连接 -> 执行查询 -> 内存拷贝二进制数据 -> 后端语言(NestJS)接收 -> 转发给用户。这会极其严重地消耗数据库的 CPU 和内存，拖慢核心的刷题接口响应速度。
- **备份机制**：完美的数据强一致性。只要用 `pg_dump` 备份数据库，图片也一起备份了。删除题目，图片连带删除，绝不会产生僵尸文件。
- **优点**：极好管理，无需维护两套系统（数据库+文件系统），数据和文件永远不会对不上号。
- **缺点**：这是**最不推荐**用来存大量 C 端图片的方案。数据库体积会因此急剧膨胀，导致常规的备份恢复变得奇慢无比；且完全无法利用 Nginx 或 CDN 的静态资源缓存加速优势。

### 方案 C：自建对象存储服务 (MinIO) - 【强烈推荐】
在你的服务器上通过 Docker 部署一个开源的 **MinIO**。它相当于在你自己的服务器上搭建了一个私有的“阿里云 OSS”。
- **性能开销**：**适中**。基于 Golang 编写，底层直接管理磁盘，性能极其强悍。资源占用高于纯 Nginx，但完全在可接受范围内。
- **备份机制**：自带极其强大的高可用与纠删码容灾机制，支持自动镜像同步。
- **优点**：
  - **接口完全标准化**：它提供了与各大云厂商完全兼容的 S3 API。在 NestJS 代码里完全按照云 OSS 的逻辑来写。这意味着，如果某天你的服务器真的撑不住了想上云，**代码一行都不用改**，直接换个 API 地址即可无缝迁移。
  - **开箱即用的可视化后台**：拥有非常漂亮的 Web UI 管理面板，你可以直观地管理、预览图库资产，还能轻松设置文件过期时间和防盗链策略。
  - **水平扩容极简**：未来若单机磁盘满了，加台新机器，MinIO 能自动帮你组建分布式集群。
- **缺点**：需要额外花 5 分钟用 Docker 部署，并会吃掉一部分服务器的内存。

### 📊 最终确认方案：【方案 A：本地文件系统 + Nginx】
- **当前决策**：采用最高效、最轻量且无额外维护成本的本地文件直接存储，通过 Nginx 对外暴露静态资源。
- **关于后期迁移的可行性**：后期从方案 A 迁移到方案 C（MinIO）或原生云 OSS 是**完全可行且非常普遍的做法**。
  - **如何保证平滑迁移**：在后续开发中，我们在 PostgreSQL 中存储图片链接时，**绝对只存相对路径**（例如 `/uploads/images/q_1001.png`）。
  - **迁移时的操作**：未来只需写个脚本把 `/uploads` 文件夹一次性上传到 MinIO 或 OSS。然后在 Nginx 配置里把 `/uploads` 的请求拦截，直接反向代理/重定向到新存储的域名即可。**后端业务代码和前端代码一行都不用改！**

## 4. 服务端架构选型 (Backend)
- **已确认方案：Node.js (NestJS 框架)**
- **核心理由**：前端使用了基于 JavaScript/TypeScript 的 Taro，后端使用 NestJS 可以实现前后端语言栈统一。NestJS 规范的模块化架构、依赖注入体系也非常适合构建这种包含题库、财务、社群等多业务模块的中大型后台。
